# 界面设计：菜单与操作流程

这份文档回答一个具体的抱怨：**「菜单有点乱，不知道怎么操作，它们之间是什么关系。」**

结论先写在前面：问题不在标签太多，而在**界面只回答了「有哪些页面」，没回答「我能做什么」**。
Word / WPS 用两套东西分别回答这两个问题——菜单管命令，选项卡管视图。本产品此前只有后者。

## 一、用户心智：从 Word / WPS 借什么

成熟内容编辑器教会用户三条稳定预期，代价已经由它们付过了，我们直接沿用：

1. **命令在菜单里，视图在别处。** 想做一件事（保存、打印、插图片、改字体）就去菜单栏找；
   菜单是「能做什么」的完整清单，找不到才怀疑功能不存在。
2. **菜单按动词分组，且顺序稳定。** 文件（对整个文档）→ 开始/编辑（对当前内容）→
   插入 → 视图 → 工具 → 帮助。用户不需要理解分组逻辑，靠位置记忆就能找到。
3. **不可用的项置灰，不隐藏。** 没选中文字时「加粗」是灰的，但**它还在原位**。
   隐藏会让人以为软件没有这个功能，比灰掉更伤。

对应到 StaticSmith 的对象模型：

- **站点 ≈ 文档**：新建 / 打开 / 最近打开 / 关闭，都是文档级动作
- **文章 ≈ 正文**：保存、加粗、插链接、插图片
- **模板与主题 ≈ 样式**：改一处影响全篇，正是 Word 里「样式」的地位
- **生成 ≈ 排版成稿**：把内容与样式渲染成 `dist/`
- **发布 ≈ 送出去**：把稿子交到线上，和「保存」不是一回事

这几条对应关系决定了菜单的分组，也解释了为什么「生成」和「发布」必须是两项而不是一项。

## 二、不做 Ribbon（功能区）的理由

WPS / Word 现在的主形态是 Ribbon：图标 + 分区 + 两行高度。我们**先做文字菜单栏**，原因有三：

- Ribbon 的收益来自命令多到一屏放不下（Word 有上千个）。本产品的命令是几十个量级，
  Ribbon 会大量留白，反而显得空。
- Ribbon 需要一整套图标语言。没有图标的 Ribbon 就是一排大按钮，比菜单更占地方也更难扫读。
- 本产品的主界面是三栏工作区（列表 / 编辑 / 预览），纵向空间比 Word 更紧张，
  两行 Ribbon 会直接压缩正文。

等命令数量真的撑不住一层菜单，再谈 Ribbon；那时候图标也该一起做。

## 三、信息架构：五层，各回答一个问题

```
┌ 菜单栏：站点 编辑 插入 视图 工具 帮助 ──────────────────────┐  ← 我能做什么（命令）
├ 标识行：站点名 · 路径 · 正在编辑 posts/x.md ● ─ 面板 生成 关闭 ┤  ← 在哪个站点 / 哪篇
├ 标签栏：写[内容 日历] 外观[外观] 上线[体检 生成 发布] 站点[设置]  当前页说明 ┤  ← 看什么
├ 工作区（内容页三栏：列表 | 编辑 | 预览）───────────────────┤  ← 干活
└ 状态栏：进度 · 未保存 · 预览地址 · 待生成 N / M ───────────┘  ← 当前状态
```

分工的硬边界：

- **菜单只放动词，标签只放名词。** 「生成」既是命令也是页面，所以它同时出现在
  菜单（执行）与标签（看报告）——这是刻意的重复，不是分裂。
- **横向条数量是有上限的。** 曾经把「当前页说明」单独做成一行，加上菜单栏之后
  固定占用逼近 160px，768p 屏的工作区只剩约 600px。所以说明并进标签栏右侧，
  窄窗口下先截断说明而不是挤走标签。**再想加一条横向条，得先删掉一条。**
- **主动作留在标识行。** Word 把「保存」放快速访问工具栏，我们把最高频的「生成」
  做成唯一的主色按钮；「关闭站点」也留在这里——它在菜单里也有，但从「一键」退化成
  「两步」是功能回退。
- **正在编辑哪篇写在标识行。** Word 的标题栏永远显示文档名；切到「体检」页之后
  编辑器不在，状态栏那个「● 未保存」不说明是谁。
- **状态栏不放动作。** 它只报告状态（待生成 N / M、未保存、预览地址）。
- **唯一允许的第六条是条件横幅。** 「检测到磁盘上的模板或内容被外部修改 [刷新组件树]」
  （`src/App.vue` 的 `.app__banner`）只在外部改动发生时出现，出现即带一个动作按钮。
  它能破「先删一条」的规矩，是因为它**不常驻**：常驻条永久收税，条件条只在有话要说时收。
  凡是新增横向条，先自问「它是不是永远都在」——是，就得先删一条；不是，就必须能自己消失，
  且必须自带解决它的那个动作（不然用户只能干看着）。

## 四、菜单规格

每个菜单的内容与理由。命令表在 `src/commands.ts`，**菜单栏与命令面板共用这一份**——
两边各写一遍迟早出现「面板里有、菜单里没有」，那正是「不知道能干什么」的来源。

- **站点**（文档级）：新建站点… / 打开站点… / 最近打开的 5 个 /
  保存当前文章（外观页看着模板时这一项变成「保存当前模板」，见 6.10） /
  生成 / 完整重建 / 在文件管理器中打开产物 / 发布… / 从别的站点导入内容… / 关闭站点。
  最近列表放在这里而不是别处，因为 Word 的「文件」菜单就是这么教用户的。
- **编辑**（对当前文章）：查找内容 / 新建文章… / 新建栏目… / 加粗 / 斜体 / 行内代码 /
  标题 / 引用 / 无序列表。没打开文章时后半段置灰。
- **插入**：链接 / 图片或附件…。**只放真正插到光标处的东西**——新建栏目是建目录，
  导入内容是搬文件，两者曾经放在这里，但点下去只是跳页，看不出「插入」了什么。
- **视图**：内容列表栏、预览栏（勾选式开关，对应 Word 的导航窗格）/ 命令面板。
  **不重复标签栏的跳转**：Word 的视图菜单也不列选项卡；搜索式跳转在命令面板的「页面」组里。
- **工具**：三种体检（SEO / 死链 / 媒体）/ 本地预览服务器启停 / 保存后自动生成 /
  重新读取磁盘。体检点下去会**先切到「体检」页再跑**——跑完停在别处等于没反馈。
- **帮助**：项目文档 / 快捷键与全部命令（打开命令面板）。

交互规则（都是桌面软件的既有习惯，用户不用学）：

- 点标题展开；**展开状态下鼠标划过就切换菜单**；Esc 或点空白处关闭
- 方向键在可用项之间循环，置灰项跳过；快捷键右对齐显示
- 不可逆或影响线上的项标红（当前只有「关闭站点」这类，删除类仍留在各自面板里就地确认）
- 危险动作不进菜单深处：批量删除、删栏目、删媒体依旧在对应面板里，且都要二次确认。
  菜单是入口，不是绕过确认的后门

## 五、三条操作流程

设计菜单的检验标准是这三条路径能不能不看文档走通。

**第一次用（从零到线上）**

1. 起始页「新建站点」→ 选目录（也可以从菜单「站点 → 新建站点…」）
2. 标签停在「内容」；侧栏「新建」写第一篇（菜单「编辑 → 新建文章…」等价）
3. 右侧预览实时看效果，`Ctrl+S` 保存
4. 顶栏「生成」（`Ctrl+Enter`）→ 状态栏的「待生成 N / M」归零
5. 「工具 → 启动本地预览服务器」在浏览器里验一眼
6. 「站点 → 发布…」配置 Git / FTP，然后发布

**日常写作**

`Ctrl+P` 找文章 → 写 → `Ctrl+S`（开了「保存后自动生成」就不用再点生成）→
预览自动刷新。要补 SEO 就去「体检」页，按清单逐条点回文章。

**接手别人的站点 / 换外观**

「站点 → 打开站点…」或「站点 → 从别的站点导入内容…」把旧站搬进来 →「外观 → 主题包」
装一套外观（先看清单再决定是否覆盖）→ 「体检」跑一遍死链 → 生成 → 发布。

## 六、视觉与交互规范

这一节是给「加一个控件时照着做」用的，收尾的 6.13 是可以逐条勾的清单。
起因是一个具体缺陷：标签栏的**分组名**与**未选中的标签**长得几乎一样，
读起来是一串连续的词，分不清哪个能点。后来按同样的方式追查了「看不见的那一半」——
焦点、反馈、空态、快捷键作用域——鼠标用户碰不到，但它们坏起来同样让人不知道怎么操作，
于是 6.7 之后几节都是这么来的。

每条规则底下都写了它的起因。**照着做的时候可以不看起因，要改规则的时候必须先看**。


### 6.1 元素分类学：三类，别混

界面上每个东西只属于一类，样式跟着类别走，不跟心情走：

- **动作**（按钮、菜单项、下拉）：点了会发生事情。必须有内边距形成可点区域，
  悬停出现「面」（背景变化），指针为手型。
- **导航**（标签页、侧栏条目、设置页分段）：点了换视图，不改数据。选中态用
  **主色下边框 / 左边框 + 字重**，**不用填充**——填充是「按下」的语义，会和动作混淆。
- **只读标注**（分组名、计数、当前页说明、状态徽标）：不可点。更小字号 + 次要色，
  `cursor: default`、`user-select: none`，永远不给悬停反馈。

**判别规则（本次缺陷的根因）**：同一行里相邻的两个元素若类别不同，
必须在「字号 / 色彩 / 间距」三项里至少差**两项**。原先分组名与未选中标签只差字号
（0.7rem vs 0.75rem），色彩同为 `--fg-muted`，间距还均匀——三项里只差半项，
于是「写 内容 日历 外观 外观」读成一排等价的词。

修正后（标签栏）：

- 间距：组内 `2px`，组间 `10px` + 竖线（格式塔接近性：组名贴着自己的标签）
- 色彩：标签用正文色 `--fg`（未选中 opacity .75），组名用 `--fg-muted` 且 opacity .75
- 字号字重：标签 `0.85rem / 500`，组名 `0.68rem / 400` 且加 `0.08em` 字距

### 6.2 排版与色彩刻度

**单位口径先定死：CSS 里一律写 `rem`，`1rem = 16px`，本节的 px 只是换算注释。**
之前这份文档写 px、代码写 rem，两套刻度并行的结果是「看着都对，量出来都不对」——
标签栏组内间距文档写 `2px`，代码是 `0.1rem`（1.6px）；组间文档写 `10px`，代码是 `0.5rem`（8px）。

字号只有三档，超出就是设计失控：

- `0.7rem`（≈11px）**标注**：分组名、计数、徽标、当前页说明
- `0.8rem`（≈13px）**正文与控件**：标签、菜单项、按钮、输入框、列表条目
- `1rem`+ **标题**：卡片标题、面板标题、起始页大字

每档允许 ±0.05rem 的微调（`0.75` / `0.85` 这类），**但不允许出现第四档**。
现状是 9 档、35 处越界（`0.68 / 0.7 / 0.72 / 0.75 / 0.76 / 0.78 / 0.8 / 0.82 / 0.85 / 0.9 / 0.95rem`
都有人用），收敛计划记在第九节。

字重三档：`400` 标注 · `500` 控件 · `600` 选中/强调。
**`700` 不在刻度里**——`<h2>` 的浏览器默认值也算越界，卡片标题要显式写 `600`。

色彩只从令牌取（清单见 6.11）：`--fg` 主体 · `--fg-muted` 次要 ·
`--accent` 仅用于**当前状态与主动作**，不用来装饰。一屏最多一个主色实心按钮。

### 6.3 间距刻度

五档，写成 rem（括号是换算）：

- `0.125rem`（2px）同类元素之间（一组标签内部）
- `0.25rem`（4px）控件内边距的纵向
- `0.375rem`（6px）控件内边距的横向、图标与文字之间
- `0.625rem`（10px）不同分组之间（同时配一条 1px 竖线）
- `1rem`（16px）面板与面板之间

**间距承载分组信息**，所以「组内比组间窄」这条不能破。均匀间距等于没有分组。
边框宽度与圆角不在这套刻度里，各自只有一个值：`1px` 边框、`10px` 圆角
（拖拽分隔条的 `6px` 是命中区，不是间距）。

### 6.4 交互状态矩阵

每类控件都要把六个状态写全，缺哪个就是哪个状态下用户会困惑：

- **动作按钮**：默认描边 → 悬停背景变 `--bg-subtle` → 焦点 `outline: 2px --accent`
  （内侧，不撑行高）→ 按下无额外位移 → 禁用置灰且 `cursor: default` → 危险动作文字标红
- **导航标签**：默认 opacity .75 → 悬停补面并升至 1 → 焦点同上 → 选中主色下边框 + 600 字重
- **勾选式菜单项**：勾号占固定宽度，有没有勾文字都对齐（否则一列文字左右抖动）
- **只读标注**：**没有**悬停、焦点、按下三态
- **禁用**一律用 `disabled` 属性而不是仅靠 `opacity`：前者键盘与读屏都能识别
- **不可用就置灰，不隐藏**：隐藏会让人以为功能不存在（Office 的老规矩）

### 6.5 文案规范

- 标签用**名词**（内容、外观、体检），菜单项用**动词**（保存、生成、装入）
- 按钮写后果，不写「确定」：`装入 11 个文件`、`创建草稿`、`导入 5 篇`
- 含义写不进两个字就用括号补全：`待生成（改过还没生成）`。
  别指望用户猜——这是内容筛选那一处返工的教训
- 数量后置括号：`全部内容（41）`；为空的选项置灰
- 悬停提示（`title`）只做补充，**不能是某条信息的唯一出处**

### 6.6 无障碍最低线

- 分组用 `role="group" + aria-label`，组名 `aria-hidden`（它是给眼睛的重复信息）
- 当前视图用 `aria-current="page"`，不靠颜色单独表达
- 所有可聚焦控件都要有 `:focus-visible` 轮廓；轮廓画在内侧，避免撑开布局
- 菜单欠账已记：缺 `role="menu"` / `menuitem` / `aria-haspopup`，在「后续」里

### 6.7 焦点与浮层

起因：命令面板是界面里唯一的浮层，但它只有 `role="dialog"`——Tab 能一路走到浮层背后的
标签栏和列表里去，关闭之后焦点掉回 `<body>`，键盘用户得从头 Tab 一遍。
鼠标用户看不见这个问题，所以它一直没被发现。

- **浮层三件套缺一不可**：`role="dialog"` + `aria-modal="true"` + Tab 在浮层内循环。
  做不到 focus trap 就不该做浮层——这其实是「只有一个浮层」那条约束的另一半理由：
  浮层的成本不在画它，在管焦点。命令面板的 Tab / Shift+Tab 现在**不移动焦点**，
  而是在候选项之间上下走（焦点始终留在输入框里）：这既是最简单的 trap，
  也符合「输入框 + 列表」这类控件的通行做法，配 `role="combobox"` +
  `aria-activedescendant` 让读屏器念出当前那一条。
- **打开即聚焦，关闭即归还。** 打开时聚焦第一个可操作元素；关闭时把焦点还给触发它的那个
  按钮或菜单项。`v-if` 销毁一个正被聚焦的元素时，浏览器不会替你归还。
  **归还只在「我不做了」时发生**（Esc、点空白）：点了某条命令则由那条命令决定焦点去哪，
  否则「查找内容」会先把焦点送到搜索框、再被菜单抢回菜单标题。
- **就地确认默认聚焦「取消」**，不是「删除」。确认态是为了拦住误操作，
  如果回车正好落在危险按钮上，这层拦阻等于没有。
- **展开式表单一律自动聚焦第一个输入框**，且必须一致：新建内容、新建栏目、改名、
  「栏目信息」四处现在都聚焦。**同类控件行为不一致，比两者都不做更伤**——
  用户会以为焦点是随机的。
- **不用 `autofocus` 属性**：它与 `v-if` 的挂载时机不同步，时好时坏。统一在 `nextTick` /
  `requestAnimationFrame` 之后调 `.focus()`。
- **焦点必须看得见。** `:focus-visible` 是硬要求，且**永远不许写 `outline: none`**。
  轮廓画在内侧（`outline-offset: -3px`），避免撑开布局或压住浮层边框。
- **菜单标题上也要能用方向键。** 左右在菜单之间走、下键进入当前菜单：只把监听挂在下拉
  容器上的话，焦点还在标题时方向键完全没反应，用户会以为方向键坏了。
- **Esc 从内往外逐层关，一次只关一层**：就地确认 → 展开表单 → 浮层 → 菜单。
  一按 Esc 全部收起，会把用户填了一半的表单一起清掉。

### 6.8 反馈与等待

起因：菜单里的「重新读取磁盘上的内容与模板」点下去**什么都不会发生**——它确实执行了，
只是成功时既不通知也不改变界面。另一头，构建结束后状态栏长期停在最后一条进度文字
（如 `render 42/42`），再也回不到「就绪」。

- **每个动作都必须有可见结果**，三选一：界面内容变了、弹了通知、或某个数字变了。
  三者都没有就等于没执行——用户下一步会再点一次。
- **通知加在命令那一层，不加在共用动作里。** 「重新读取磁盘」现在会报一条，
  但通知写在 `commands.ts` 的 `refreshFromDisk()` 而不是 `actions.refresh()`：
  后者被保存、批量、导入、生成复用，加进去等于每次保存都弹。
  同理，三种体检用 `announce` 参数区分「人主动点」与「顺带重跑」。
- **忙态要盖住整段操作。** 忙态标志必须是**计数器**（进入 +1、退出 −1、归零才算完），
  不能是布尔：`build` 内部嵌套三层执行，布尔标志会在一次点击里 true/false 跳变好几次，
  按钮闪烁、`disabled` 提前解除，用户可能在中途二次点击。
  光有计数器还不够：复合动作里的几次调用是**顺序**而非嵌套的，每步之间计数照样归零，
  所以复合动作要在入口用 `busySpan()` 先占一格（保存、生成、批量、打开站点都已包上）。
  判据：函数体里出现两次以上 `run`/`await this.xxx` 就该包。
- **进度是过程量，必须归零。** 操作结束就清空进度文字，让状态栏回到「就绪」。
  停在旧进度上比不显示进度更糟：它看起来像「还在跑」。清空写在忙态归零的同一处，
  不散落到各个动作里——散开就一定有漏的那一个。
- **通知的三个参数写死**：错误停 8s、成功与提示停 3.5s、都可手动关闭。
  同屏最多 3 条，超出的合并成「另有 N 条」；生成警告已合并成一条
  （`N 条生成警告：第一条 等`），逐条弹能刷满一屏。
- **批量结果一条通知讲完**：「改了 5 篇，跳过 2 篇（目标已存在）」。
  逐条弹通知是把汇总工作推给用户。
- **错误有两个出口，别混：** 瞬时的、重试即可的用通知；需要用户处置的（配置缺失、
  路径无效）要**留在界面上**直到解决。留在界面上的那一份现在只有起始页的 alert
  ——打不开站点时那句话必须留着，通知飘走了用户就不知道为什么进不去。主界面里
  可处置的错误就地显示在出问题的那一块（设置页字段旁、发布面板内），
  不做全局常驻错误条：一条与上下文脱节的红条，用户既不知道是谁报的、也不知道怎么消。
- **自己补齐前置条件，并说出正在补什么。** 点产物预览会自动拉起本地服务器，这是对的；
  但期间只有一个忙态，没人知道在等什么。缺一句「正在启动本地预览服务器…」。

### 6.9 空态：分档，别共用一句

起因：内容列表把空态分成三档（搜不到 / 该筛选类为空 / 全站还没有内容），这是对的；
而外观页的四个列表是裸循环，空的时候页面上只剩四个孤零零的标题，看起来像加载失败。

- **每个列表都要有空态分支。** 列表为空是常态（新站点、被筛掉、还没生成），不是异常。
- **按原因分档，每档给不同的出路：** 无数据 → 给创建入口；被筛掉 → 给「清除筛选」；
  未生成 → 说明「生成之后这里会出现什么」。同一句「暂无数据」应付三种原因，
  等于三次都没回答用户的问题。
- **不要用「整块消失」当空态。** 发布面板从未发布时的结果区、构建历史的空表、
  「站点页面（生成）」在没有产物时的整组隐藏——它们和「新建栏目之后栏目当场消失」
  （见 `ui.md` 的侧栏一节）是同一个错：**消失让人以为功能不存在**，
  和 6.4「不可用就置灰，不隐藏」是同一条原则在列表上的形态。这三处已改成留标题 + 一句出路。
- **空态文案写「接下来做什么」**，不写「暂无数据」。参照 6.5：按钮写后果，空态写出路。
- **空态也有它的空态：** 全新站点里连一篇文章都没有时，不必再提「生成之后会有标签页」——
  那时唯一该说的是「写第一篇」。空态提示要挑当前最该做的那一件，堆三条等于没有重点。
- 样式只有一份：`.empty-hint`（弱化色 + 0.85rem）跨面板共用，不给每块各写一个
  `xxx__empty`——空态的写法只该有一种。

### 6.10 键盘与快捷键的作用域

起因：在编辑器里按 `Ctrl+F` 想搜正文，焦点被弹到侧栏的内容搜索框——全局监听器没有看
「按下时焦点在哪」。更隐蔽的是这条快捷键**依赖侧栏挂载**：关掉列表栏或切到别的标签页，
`Ctrl+F` 完全无效，而文档里它是无条件列出的。

- **快捷键分三层，注册时必须明确属于哪一层：** 全局（在根组件注册，任何时候可用）、
  页面级（组件挂载期间有效）、控件级（焦点在该控件内有效）。
  同一个键只许注册一层：`Ctrl+S` 曾经在编辑器的 textarea 上也注册过一次，
  而 textarea 的事件会继续冒泡到 window——两层都留着就会保存两次。
- **全局层拦截前先看 `event.target`。** 焦点在 `textarea` / `input` /
  `[contenteditable]` 里时，控件与浏览器的原生行为优先——正在打字的人按 `Ctrl+F`
  想搜的是眼前这段文字。**当前的例外：** 正文内查找还没实现，`Ctrl+F` 在整个应用里
  只有「找文章」一个含义，所以暂不区分焦点；等正文内查找落地，编辑器内的 `Ctrl+F`
  归正文，找文章让给 `Ctrl+Shift+F`。
- **页面级快捷键不许悄悄失效。** 它要么自己补齐前置条件（切到对应标签页 + 打开被关掉的
  面板，同 6.8 最后一条），要么就别在帮助与文档里承诺。「点了没反应」比「没有这个快捷键」
  更让人怀疑软件坏了。`Ctrl+F` 现在走 `focusSearch()`：先切页、必要时把列表栏打开，
  再聚焦并选中已有关键词。
- **同一功能只有一种语义。** `Ctrl+P` 现在是 toggle，标识行的按钮是 open：
  面板开着时点按钮没反应，用户会以为按钮坏了。二者都应是「打开并聚焦」。
- **一个「保存」，按上下文分派落点。** `Ctrl+S`、菜单项、工具条按钮都取
  `saveTarget()`：外观页看着模板时存模板，其余存文章。菜单项标题跟着变
  （「保存当前模板」／「保存当前文章」），因为「按下去会存谁」必须看得见而不是猜。
- **文档里写的快捷键必须真实存在。** 「`Ctrl+S` 保存模板」曾经是文档写了、代码没有，
  外观页只有按钮。**文档承诺一个不存在的快捷键，比没有快捷键更伤信任。**
- **菜单的键盘操作要能进得去。** 方向键的监听要挂在可聚焦的元素上，
  否则展开菜单后必须先 Tab 一下方向键才生效——那时用户已经用鼠标了。
- 快捷键一律在菜单项右侧对齐显示（见 6.4），命令面板是它们的完整清单。

### 6.11 色彩令牌与深色模式

起因：深色模式**早就实现了**（跟随 `prefers-color-scheme`），但两份文档一个字没提；
而主色与警告色没有深色覆盖，砖红 `#b7410e` 落在近黑底上对比度不够。

令牌是唯一的取色来源，新增令牌必须同时给两套值：

- `--fg` 主体文字 · `--fg-muted` 次要与标注 · `--border` 描边与分隔
- `--bg` 内容区 · `--bg-subtle` chrome（工具条、标题行、标签栏、状态栏）
- `--accent` 当前状态与主动作 · `--warn` 警告 · `--danger` 危险与不可逆

规则：

- **CSS 里不写字面色值。** 现有几处硬编码（白色文字、成功绿、危险红）是欠账，
  它们在深色下不会跟着变。
- **主色与警告色也要过对比度**：正文对底 ≥ 4.5:1，大字与描边 ≥ 3:1。
  `--accent` / `--warn` 缺深色值这一条按此判定为待修，不是「看着还行」。
- **跟随系统，不做手动切换开关。** `color-scheme: light dark` 已经让原生控件跟着走；
  要做开关，得先回答「记在哪、与系统冲突时听谁的」，收益不值这两个问题。
- 状态色不能只靠颜色表达（6.6）：草稿、定时、待生成的徽标都要有文字或形状差异。

### 6.12 动效：近乎为零，这是决定

现状全站只有一条过渡（拖拽分隔条的背景色 `0.15s`），展开、关闭、浮层全是硬切。
写下来是因为这是**取舍**，不是遗漏——不然后人会当成缺陷去「补齐」。

- 桌面工具的动效预算给「看清结构变化」，不给愉悦感。展开列表等 200ms 才看到内容，
  比立刻看到更烦，而这个界面每天要展开几十次。
- **允许两类**：悬停 / 焦点的颜色过渡（≤ 150ms），以及位置变化的位移（列表重排、
  分栏拖动）。淡入淡出、缩放、弹跳都不做。
- 一旦引入超过 150ms 的动效，**同时**补 `prefers-reduced-motion: reduce` 分支。
  现在没有动效所以没有这个分支，规则先立在这里。
- 硬切的代价要用别的手段补：内容突然变了要有 6.8 的可见结果（通知或数字变化），
  不能靠一个用户没看见的淡入来交代。

### 6.13 加控件前的自查清单


1. 它属于三类中的哪一类？样式是否照该类走？
2. 与相邻的不同类元素，是否在字号 / 色彩 / 间距里差了至少两项？
3. 六个状态是否都定义了？禁用是否用了 `disabled`？
4. 文案是名词还是动词，是否与类别一致？后果写清楚了吗？
5. 是否新增了一条横向条？若是，它常驻吗——常驻就先删一条，不常驻就得能自己消失
   并自带解决它的动作（见第三节）。
6. 键盘能不能到达并操作？焦点看得见吗？有没有写 `outline: none`？
7. 它是浮层吗？三件套（`role="dialog"` / `aria-modal` / Tab 循环）齐了吗？
   打开聚焦哪里、关闭把焦点还给谁？
8. 点下去有可见结果吗（界面变了 / 弹了通知 / 数字变了）？失败走的是哪个出口？
9. 它是列表吗？三档空态（无数据 / 被筛掉 / 未生成）各自的出路写了吗？
10. 用了新的字号 / 间距 / 颜色吗？在 6.2、6.3 的刻度与 6.11 的令牌里能找到吗？
    新令牌给了亮 / 深两套值吗？
11. 加了快捷键吗？属于全局 / 页面 / 控件哪一层？会不会抢走正在打字的人的按键？
    页面级的话，前置条件由它自己补齐吗？
12. 加了动效吗？超过 150ms 就得连 `prefers-reduced-motion` 一起加（见 6.12）。


## 七、明确不做的事，以及为什么

- **不做 Ribbon**：理由见第二节。命令规模不够，图标成本也不该现在付。
- **不做「撤销/重做」菜单项**：编辑器里 `Ctrl+Z` 由浏览器的 textarea 原生提供，
  而**跨文件的撤销栈**（撤销一次批量移动）是另一回事——Git 才是那个层面的安全网，
  假装有一个半可靠的撤销比没有更危险。
- **不把删除类动作搬进菜单**：删文章、删栏目、删媒体都需要「看清对象再确认」，
  菜单离对象太远。它们留在各自面板里就地确认。
- **不在菜单里重复标签栏的跳转**：Word 的视图菜单也不列选项卡。跳转的正规入口是标签栏，
  搜索式跳转在命令面板的「页面」组。
- **右键上下文菜单**：原先在这里写「不做（暂时）」，并留了条件「等条目动作多到放不下再说」。
  条件已达成，现在做了——理由与做法见第八节复盘的最后一条。
- **不做 Alt 加速键**（`Alt+F` 展开站点菜单）：WebView 里 Alt 组合键与系统菜单
  冲突的处理方式各平台不一，收益也低于方向键 + 命令面板。

## 八、复盘：菜单栏落地后又改了什么

第一版菜单栏上线后自查线框图，发现四类问题并当场修掉，记下来免得再犯：

- **横向条越加越多**：菜单栏 + 标识行 + 标签栏 + 说明行 + 状态栏 ≈ 160px 固定占用，
  768p 屏工作区只剩约 600px。说明行并进标签栏右侧（省 26px），并立下规矩：
  **再加一条横向条，得先删一条。**
- **视图菜单重复了标签栏**：七个「切换到…」是噪音，删掉，改由命令面板的「页面」组承担。
- **「插入」里混进了跳转**：「栏目」「导入内容」点下去只是切页，不是插入。
  前者归「编辑 → 新建栏目…」，后者归「站点」。
- **「关闭项目」从按钮退化成菜单两步**：找回标识行的按钮。功能回退比布局不齐更伤。
- **切走后不知道正在编辑哪篇**：标识行补「正在编辑 posts/x.md ●」。
- **分组名与未选中标签长得一样**：这一条催生了第六节的规范。修法是把「间距 / 色彩 /
  字号」三项拉开（原先只差半项），并给分组套 `role="group"`、组名 `aria-hidden`。
- **内容筛选的五个药丸太占地方且说不清作用**：改成一行下拉，选项文字把含义写全
  （「待生成（改过还没生成）」），正在筛选时描边变色。
- **右键：从「不做」改成「做了」**。第七节原先写「不做右键（暂时）」，理由是
  「两处入口不一致的维护成本」，并留了条件「等条目动作多到放不下再说」。
  条件已达成：分组头挤着「信息 / 改名 / ×」三个图标，而条目那一层只有一个「×」，
  其余动作全靠批量条——两头都不对。现在做了右键，并用四条把当初担心的成本消掉：
  - 右键与「⋯」按钮**触发同一份条目**（`pageMenu()` / `sectionMenu()`），不写两遍
  - 菜单项形状与菜单栏共用 `MenuEntry`：置灰、勾选、危险标红只有一份实现
  - 只放**针对眼前这个对象**的动作，全局动作仍在菜单栏。右键是看不见的入口，
    所以每处右键都配一个可见的「⋯」孪生入口——否则等于把功能藏起来
  - 删除类仍走**就地确认**：菜单项只把那一行切进确认态，不直接删。
    菜单里直接删等于绕过第七节第三条的拦阻
  换来的紧凑：分组头从「信息 / 改名 / ×」三个图标降到「信息 / ⋯」两个，
  条目那一层的「×」换成「⋯」（一个图标，但从「只能删」变成「全部动作」）。

## 九、欠账：规范已定，代码未到

第六节新增的几节是照着代码现状写的，所以有一批「规范说了、实现还没跟上」的差额。

- 外观页四个列表（主布局 / 全局共享组件 / 页面模板 / 继承结构）各有自己的空态一句话，
  按原因分档：没有主布局 → 指向主题包；没有共享组件 → 说 `partials/` 怎么用；
  继承结构空着时区分「还没有主布局」与「还没选主布局」
- 构建历史空着时说清「生成之后这里会记录什么、拿来干什么」，不再是一张空表
- 发布面板未发布时留下标题与一句说明，不再整块消失
- 「站点页面（生成）」在没有产物时保留分组并说明「按 Ctrl+Enter 生成一次就会出现」；
  全新空站点（一篇文章都没有）例外，那时唯一该说的是「写第一篇」
- 空态样式统一到 `.empty-hint`，不给每块各写一个 `xxx__empty`

**已清（焦点这轮）**

- 命令面板补 `aria-modal`；Tab / Shift+Tab 在候选项之间走（焦点留在输入框，这就是 trap），
  配 `role="combobox"` + `role="listbox"` + `aria-activedescendant`；输入框的
  `outline: none` 换成内侧焦点环
- 浮层与菜单关闭后归还焦点，且只在「我不做了」时归还（Esc、点空白）；
  点了命令则由那条命令决定焦点去哪
- 菜单标题上的方向键：左右换菜单、下键进入当前菜单，不再需要先 Tab 一下
- 改名与「栏目信息」表单展开即聚焦第一个输入框，与新建两处对齐；
  两处就地删除确认出现时聚焦「取消」

**一、刻度与令牌漂移**

- 字号 9 档、约 35 处越出三档；`<h2>` 走浏览器默认 `700`，超出字重三档
- 间距全用 rem 且落在档位之间（`0.1 / 0.3 / 0.5 / 0.6 / 0.9rem`），
  标签栏组内 1.6px、组间 8px 与 6.3 不符；组间那条 1px 竖线也要一起核
- `--accent` / `--warn` 缺深色值；几处字面色值（白、成功绿、危险红）绕过令牌
- 标识行与状态栏共用同一套 CSS 值，而 `ui.md` 写的是分别定义

**二、结构与一致性**

- 编辑动作的**文案**还是两套（菜单「标题（二级）」vs 工具条「H2」）；定义已经合并成
  一份 `editorCommands`，标签却各写各的
- 工具条有「媒体库」，「插入」菜单没有对应项
- 分栏宽度每次变化即写入存储，无防抖；窗口缩小时不重新夹取，预览栏可能超宽

**三、还没做的设计**

- 首次打开的引导：把第五节第一条路径做成可点的三步提示，而不是只写在文档里
- 正文内查找与替换：现在 `Ctrl+F` 只能找文章，找不到「这一篇里的某个词」
- 深色模式已经在跑（跟随系统），但从未按 6.11 的对比度要求逐屏核过一遍
