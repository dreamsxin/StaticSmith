# 界面设计：菜单与操作流程

这份文档回答一个具体的抱怨：**「菜单有点乱，不知道怎么操作，它们之间是什么关系。」**

结论先写在前面：问题不在标签太多，而在**界面只回答了「有哪些页面」，没回答「我能做什么」**。
Word / WPS 用两套东西分别回答这两个问题——菜单管命令，选项卡管视图。本产品此前只有后者。

## 一、用户心智：从 Word / WPS 借什么

成熟内容编辑器教会用户三条稳定预期，代价已经由它们付过了，我们直接沿用：

1. **命令在菜单里，视图在别处。** 想做一件事（保存、打印、插图片、改字体）就去菜单栏找；
   菜单是「能做什么」的完整清单，找不到才怀疑功能不存在。
2. **菜单按动词分组，且顺序稳定。** 文件（对整个文档）→ 开始/编辑（对当前内容）→
   插入 → 视图 → 工具 → 帮助。用户不需要理解分组逻辑，靠位置记忆就能找到。
3. **不可用的项置灰，不隐藏。** 没选中文字时「加粗」是灰的，但**它还在原位**。
   隐藏会让人以为软件没有这个功能，比灰掉更伤。

对应到 StaticSmith 的对象模型：

- **站点 ≈ 文档**：新建 / 打开 / 最近打开 / 关闭，都是文档级动作
- **文章 ≈ 正文**：保存、加粗、插链接、插图片
- **模板与主题 ≈ 样式**：改一处影响全篇，正是 Word 里「样式」的地位
- **生成 ≈ 排版成稿**：把内容与样式渲染成 `dist/`
- **发布 ≈ 送出去**：把稿子交到线上，和「保存」不是一回事

这几条对应关系决定了菜单的分组，也解释了为什么「生成」和「发布」必须是两项而不是一项。

## 二、不做 Ribbon（功能区）的理由

WPS / Word 现在的主形态是 Ribbon：图标 + 分区 + 两行高度。我们**先做文字菜单栏**，原因有三：

- Ribbon 的收益来自命令多到一屏放不下（Word 有上千个）。本产品的命令是几十个量级，
  Ribbon 会大量留白，反而显得空。
- Ribbon 需要一整套图标语言。没有图标的 Ribbon 就是一排大按钮，比菜单更占地方也更难扫读。
- 本产品的主界面是三栏工作区（列表 / 编辑 / 预览），纵向空间比 Word 更紧张，
  两行 Ribbon 会直接压缩正文。

等命令数量真的撑不住一层菜单，再谈 Ribbon；那时候图标也该一起做。

## 三、信息架构：五层，各回答一个问题

```
┌ 菜单栏：站点 编辑 插入 视图 工具 帮助 ──────────┐  ← 我能做什么（命令）
├ 标识行：站点名 · 路径 ─────── 命令面板 生成 ────┤  ← 我在哪个站点 + 主动作
├ 标签页：写[内容 日历] 外观[外观] 上线[体检 生成 发布] 站点[设置] ┤  ← 我在看什么（视图）
├ 当前页一句话说明 ─────────────────────────────┤  ← 这一页是干什么的
├ 工作区（内容页三栏：列表 | 编辑 | 预览）───────┤  ← 干活
└ 状态栏：进度 · 未保存 · 预览地址 · 待生成 N / M ┘  ← 当前状态
```

分工的硬边界：

- **菜单只放动词，标签只放名词。** 「生成」既是命令也是页面，所以它同时出现在
  菜单（执行）与标签（看报告）——这是刻意的重复，不是分裂。
- **主动作留在标识行。** Word 把「保存」放快速访问工具栏，我们把最高频的「生成」
  做成唯一的主色按钮；菜单里也有，但手不必去菜单。
- **状态栏不放动作。** 它只报告状态（待生成 N / M、未保存、预览地址）。

## 四、菜单规格

每个菜单的内容与理由。命令表在 `src/commands.ts`，**菜单栏与命令面板共用这一份**——
两边各写一遍迟早出现「面板里有、菜单里没有」，那正是「不知道能干什么」的来源。

- **站点**（文档级）：新建站点… / 打开站点… / 最近打开的 5 个 / 保存当前文章 /
  生成 / 完整重建 / 在文件管理器中打开产物 / 发布… / 关闭站点。
  最近列表放在这里而不是别处，因为 Word 的「文件」菜单就是这么教用户的。
- **编辑**（对当前文章）：查找内容 / 新建文章… / 加粗 / 斜体 / 行内代码 /
  标题 / 引用 / 无序列表。没打开文章时后半段置灰。
- **插入**：链接 / 图片或附件… / 栏目 / 从别的站点导入内容…。
  「粘贴或拖入编辑器」在提示里写明——菜单负责让人知道能做，快捷路径仍是拖拽。
- **视图**：内容列表栏、预览栏（勾选式开关，对应 Word 的导航窗格）/ 命令面板 /
  切换到各页面（带勾选表示当前页）。
- **工具**：三种体检（SEO / 死链 / 媒体）/ 本地预览服务器启停 / 保存后自动生成 /
  重新读取磁盘。体检点下去会**先切到「体检」页再跑**——跑完停在别处等于没反馈。
- **帮助**：项目文档 / 快捷键与全部命令（打开命令面板）。

交互规则（都是桌面软件的既有习惯，用户不用学）：

- 点标题展开；**展开状态下鼠标划过就切换菜单**；Esc 或点空白处关闭
- 方向键在可用项之间循环，置灰项跳过；快捷键右对齐显示
- 不可逆或影响线上的项标红（当前只有「关闭站点」这类，删除类仍留在各自面板里就地确认）
- 危险动作不进菜单深处：批量删除、删栏目、删媒体依旧在对应面板里，且都要二次确认。
  菜单是入口，不是绕过确认的后门

## 五、三条操作流程

设计菜单的检验标准是这三条路径能不能不看文档走通。

**第一次用（从零到线上）**

1. 起始页「新建站点」→ 选目录（也可以从菜单「站点 → 新建站点…」）
2. 标签停在「内容」；侧栏「新建」写第一篇（菜单「编辑 → 新建文章…」等价）
3. 右侧预览实时看效果，`Ctrl+S` 保存
4. 顶栏「生成」（`Ctrl+Enter`）→ 状态栏的「待生成 N / M」归零
5. 「工具 → 启动本地预览服务器」在浏览器里验一眼
6. 「站点 → 发布…」配置 Git / FTP，然后发布

**日常写作**

`Ctrl+P` 找文章 → 写 → `Ctrl+S`（开了「保存后自动生成」就不用再点生成）→
预览自动刷新。要补 SEO 就去「体检」页，按清单逐条点回文章。

**接手别人的站点 / 换外观**

「站点 → 打开站点…」→「设置 → 导入内容」把旧站搬进来 →「外观 → 主题包」装一套外观
（先看清单再决定是否覆盖）→ 「体检」跑一遍死链 → 生成 → 发布。

## 六、明确不做的事，以及为什么

- **不做 Ribbon**：理由见第二节。命令规模不够，图标成本也不该现在付。
- **不做「撤销/重做」菜单项**：编辑器里 `Ctrl+Z` 由浏览器的 textarea 原生提供，
  而**跨文件的撤销栈**（撤销一次批量移动）是另一回事——Git 才是那个层面的安全网，
  假装有一个半可靠的撤销比没有更危险。
- **不把删除类动作搬进菜单**：删文章、删栏目、删媒体都需要「看清对象再确认」，
  菜单离对象太远。它们留在各自面板里就地确认。
- **不做右键上下文菜单**（暂时）：内容列表的每一行已经有悬停显形的动作，
  再加一层右键会出现「两处入口不一致」的维护成本。等条目动作多到放不下再说。
- **不做 Alt 加速键**（`Alt+F` 展开站点菜单）：WebView 里 Alt 组合键与系统菜单
  冲突的处理方式各平台不一，收益也低于方向键 + 命令面板。

## 七、后续

- 首次打开的引导：把第五节第一条路径做成可点的三步提示，而不是只写在文档里
- 编辑器工具条：现在加粗/插图这些命令在菜单与快捷键里，写作时手要离开键盘去菜单。
  等确认哪几个真的高频，再在编辑器上方放一条最小工具条（不超过 6 个）
- 命令面板的最近使用排序：目前是固定顺序 + 子串匹配，够用；等命令数量再涨一档再考虑
