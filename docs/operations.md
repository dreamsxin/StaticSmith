# 站点运营手册：日常动作、现有能力与缺口

这份文档不讲实现，讲**站点维护者与内容运营者每天要做什么**，以及这些动作在
StaticSmith 里对应哪个入口。最后一节老实列出还缺什么、为什么现在没做——
路线图不该只有「已完成」。

两种角色其实是同一个人在两个时刻：

- **维护者**：管结构与链路。栏目怎么分、模板怎么继承、地址长什么样、怎么发上线。
  动作低频但影响全站，出错代价高。
- **运营者**：管产出与效果。选题、写、补 SEO 字段、定时发、事后复盘。
  动作高频且重复，效率与「别让我忘事」最重要。

工具的分工也照这条线走：**低频高风险的动作要显式、可预览、可回滚；
高频动作要少点几下、并主动提醒漏掉的东西。**

## 一、接手一个站点

| 要做的事 | 现在怎么做 |
| --- | --- |
| 从零起站 | 起始页「新建站点」或 `staticsmith init --preset docs\|blog`，两套版式各带一套可用模板与示例内容 |
| 打开已有站点 | 起始页选目录；最近列表按打开时间排序，忘了放哪也能找回 |
| 确认能正常构建 | `staticsmith check`（模板/内容/配置能否加载，顺带报草稿与定时篇数） |
| 摸清结构 | 内容侧栏按栏目分组；「外观」页看布局→组件继承关系；MCP 的 `site_info` 给 Agent 一次性交底 |
| 搬来已有内容 | 「设置 → 从别的站点导入内容」或 `staticsmith import <目录>`，Hugo / Jekyll 的 YAML front matter 转成 TOML |
| 换一套外观 | 「外观 → 主题包」选包后先看清单，或 `staticsmith theme import <包.zip> --dry-run`；把现有外观带走用 `theme export` |

从别家搬内容（桌面端向导与 `staticsmith import` 同一套判断）遵守三条：

- **正文一个字节都不动**，只重写围栏里的元数据
- **不认识的字段不丢**：转不了的（嵌套映射、`layout` 等）原样写成 TOML 注释留在文件里，
  并在报告里列成警告——导入完你能一眼看到「哪几篇需要人看一下」
- **先扫后导**：`--dry-run` 只读，逐篇给出「会写到哪、front matter 变成什么样」；
  真导入时目标已存在则跳过，绝不覆盖

顺手处理的别家约定：Jekyll 的 `2026-03-05-标题.md`（日期进 front matter、文件名去掉前缀）、
`published: false` → `draft = true`、`2026-02-03 10:20:00 +0800` 这类日期归一成 RFC3339
（没写时区的按 UTC 并给出警告）。`layout` **不猜**：别家的模板名映射错会让整页渲染错，
只提示你自己写 `template`。


站点的一切状态都在目录里（`content/`、`templates/`、`themes/`、`static/`、
`staticsmith.toml`），没有隐藏的数据库。这样接手成本最低：`git clone` 完就是全部。
`.staticsmith/index.db` 只是增量构建的缓存，删掉不影响正确性。

## 二、组织结构

**栏目就是 `content/` 下的一层目录**，栏目索引页（`index.md` / `_index.md`）
决定这个栏目的列表页。文章模板由文件位置约定推导，新增栏目**不需要新模板**。

内容侧栏的分组头上有四个动作（悬停显形）：

- **新建栏目**：建目录 + 同时生成索引页。没有索引页的栏目文章能访问、栏目地址
  却是 404，所以两件事一起做；已有栏目缺索引页时分组头会挂「缺列表页」徽标。
- **栏目信息**：改标题、简介与排序权重。这三项写在索引页的 front matter 里——
  栏目就是目录，它的介绍该在那张列表页上，不另开一个栏目配置文件。简介同时是
  列表页的 SEO 描述；权重决定栏目在侧栏与模板 `sections` 里的先后（小的在前，
  都不填就按路径）。缺索引页的栏目保存时会顺手补一张。
- **栏目改名**：整棵子树搬到新名字下，并**默认给每篇文章补 `aliases`（旧地址）**，
  构建后旧地址是重定向页，站外老链接与搜索结果继续可用。这是「整理结构」最容易
  砸到自己脚的地方，所以默认就帮你兜住。
- **删除栏目**：只删空栏目。里面还有文章时直接报错，不做「连带删除二十篇」这种
  一键灾难；要清空请先逐篇删除或搬走。

同一套能力在 Agent 侧是 `list_sections` / `create_section` / `rename_section`
（见 [MCP](mcp.md)）。**删栏目不开给 Agent**——删目录不可逆，留给人在界面里确认。

横向分类走 taxonomy：`[[taxonomies]]` 可配多个维度（标签、分类……），
在「设置」里按列表编辑，见 [配置说明](configuration.md)。

**新栏目要出现在导航里**，去「设置 → 导航菜单」加一行（名称 + 地址，上移下移排序）。
导航是配置（`[[menu]]`）而不是模板里的一串死链接，所以加栏目不用碰
`components/header.html`——那是全站组件，一改就是全站重新生成。
分类维度不用手动登记，模板自己按 `taxonomies` 列出。

## 三、写作与发布节奏

- 新建默认是**草稿**（`draft = true`），写一行不会被推上线。
- 「属性」面板集中填 `title` / `date` / `description` / `tags` / `keywords` / 旧地址，
  改动折算回源文，正文与注释原样保留。
- 定时发布：`[build] publish_future = false` 后，`date` 未到的文章不进产物、
  不进列表与订阅，配合定时 CI 构建到点上线；列表里带「定时」徽标与同名筛选。
- 「日历」标签页把 `date` 摊在月历上：本月发了几篇、下周排了什么、距上次发布几天，
  以及**没写日期的那些**（它们一律被当成已到时间，不点出来就等于藏了一批稿子）。
  这一页只呈现，判断仍来自构建侧，不会与列表里的徽标打架。
- 「保存即生成」+ 预览自动刷新（保留滚动位置）：改完立刻能看到最终效果。
- 内容侧栏的筛选（草稿 / 待生成 / 待补 SEO / 定时）把「还欠什么」变成一次点击。

**批量动作**（内容侧栏「多选」）：勾选若干篇后可以

- 批量加/去标签：加什么、去什么分开填，各篇原有的标签不会被洗掉
- 批量发布 / 收回草稿：已经是目标状态的会被跳过，不白写盘
- 批量移动到栏目：默认补旧地址，构建后老链接经重定向页继续可用
- 批量删除：需要就地二次确认

三条约定：**逐篇独立**（一篇失败不影响其余，结果分「改了几篇」与「跳过几篇及原因」）、
**只动该动的键**（正文与其他键原样保留）、**每次动作后清空选择**（文件可能已经搬走或删掉，
旧的选中集没有意义）。

**搬动与删除先干跑**：点「移动…」或「删除…」不会立刻落盘，而是先列出「哪几篇会怎么变、
旧地址是什么、哪几篇不会动及原因」，确认后才执行。判断与执行共用一份逻辑，
所以预览说会改的就一定会改。加标签、切草稿不走这一步——它们反手就能改回来，
多一次确认只是白点一下。

**没有撤销栈**，这是明确的取舍：批量改的是磁盘上的源文，做一份可靠的反向操作等于
自己实现一个小型版本控制，而内容本来就该放在 Git 下（`git diff` / `git checkout`
比任何自制 undo 都可靠）。所以工具的责任是：不可逆的动作先给预览，做完把
「改了什么、跳过什么、为什么」说清楚。



## 四、上线前的例行检查

三份体检共用一套规则，桌面端、MCP、CLI 结论一致：

- **SEO 体检**：标题、描述、关键词、正文长度、重复标题/描述、站点级配置
- **站内死链**：读产物，找点了会 404 的链接（不发网络请求）
- **媒体资源**：没人引用的文件（可回收）与引用了却不存在的地址（破图）

CI 门禁：`staticsmith audit --build`，`--fail-on` 默认只在必须修的问题上变红
（死链与破图算必须修）。细节见 [SEO 与内容运营](seo.md) 与 [命令行工具](cli.md)。

## 五、改地址与迁移

改地址是运营里最容易留下长期伤害的动作：

1. 改单篇的 `slug` → 在属性面板「旧地址」里填上原来的地址
2. 改栏目名 → 用栏目改名（默认自动补旧地址）
3. 改完 `build` 一次，再看一遍死链体检

`aliases` 生成的重定向页是 `meta refresh` + 指向新地址的 `canonical` + `noindex`，
让搜索引擎把权重并到新地址。**删掉某个 alias 后旧的重定向页不会自动清理**
（与分页产物同样的已知行为），需要时做一次完整重建。

## 六、把重复劳动交给 AI

程序不内置大模型：那会把 API Key、网络出口与内容隐私一起塞进桌面应用。
做法是通过 MCP 把站点能力开放给你已经在用的 Agent，权限分三档
（只读 / `--allow-write` / `--allow-deploy`），写内容优先用
`patch_front_matter` 这种「只改指定字段」的窄接口，而不是整文覆盖。

典型任务：批量补描述与关键词、按体检清单逐篇修、改名后补旧地址。

## 七、发布

Git 或 FTP/SFTP，凭据在桌面端进系统凭据管理器、在 CI 走环境变量，配置文件里
只存变量名。发布前可只做连接检查（`--check-only`）。见 [发布机制](deploy.md)。

## 还缺什么

按「运营者多久会撞一次」排序。每条都写清为什么现在没做，避免下次重新纠结。

1. **更多导入来源**。Hugo / Jekyll 的 Markdown 目录已经能导（命令行 `staticsmith import`、
   桌面端「设置 → 从别的站点导入内容」），但 WordPress 导出的 XML、
   Notion / 语雀的压缩包还不认——每种来源的资源引用方式都不同，
   要一种一种验证过再说支持。
2. **栏目封面与自定义元信息**。标题、简介、排序已经能在界面里改，封面图这类字段
   仍要手写进索引页的 front matter（会落在 `page.extra` 里，模板自取）。
   界面没做通用的「任意键值编辑器」：那等于把 TOML 表单化一遍，
   而每个站点真正需要的自定义字段只有一两个。
3. **导航菜单的分组与二级菜单**。一级菜单已经是配置驱动（`[[menu]]`，见
   [配置](configuration.md)），下拉分组还没做：那要先定「分组是嵌套数组还是 parent 字段」，
   而多数个人站根本用不到二级菜单，先不猜。
4. **多站点：一窗口一站点**。事件层已经按窗口标签定向，`AppState` 仍是单 session；
   要把它换成按标签索引的表，并逐个命令带上窗口身份。
5. **DOM 级热更新**。现在是整页自动重载 + 保留滚动位置，够用但不够顺；
   做局部替换需要在产物里注入更多运行时，与「产物即最终站点」的原则要谈判。
6. **资源自动回收**。媒体体检 + 人工确认删除已经有了，「构建时自动清理」
   刻意没做：自动删文件一旦判错（比如只在 JS 里拼出来的图片地址）就是数据丢失。
7. **i18n 多语言构建**。主题包已经能打包与安装（桌面端「外观 → 主题包」，
   命令行 `staticsmith theme export` / `import`）；多语言要先定
   「一篇文章的多语言版本是同一个文件还是多个文件」，是结构性决定，定错要返工整套内容层。
8. **批量动作的更多干跑覆盖**。搬动与删除已经先预览再落盘（判断与执行同源），
   加标签、切草稿仍是直接执行——它们可逆，暂时不值得多一次点击。
   若以后加入「改正文」这类批量动作，必须一并纳入干跑。
9. **日历里直接改日期**（拖动条目改期）。现在只能点进文章去属性面板改。
   拖拽要处理「拖到过去等于立刻发布」这类语义，先看有没有人真的按周排期再说。




想补哪一条，先在 [开发指引](development.md) 里对齐范围，再动手。
